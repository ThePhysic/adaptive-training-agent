# F0 contract B — Candidate lifecycle, revision, expiry and atomic approval

**Status:** proposed owner sign-off; normative for F1 after ratification. Closes C2 and clarifies C5 of review 11. This contract is **single API process, one worker, localhost-only synthetic identity**; it is not a multi-replica design. Preferred F1 local topology: run the API bound to host `127.0.0.1` and PostgreSQL in a Docker container with appropriately restricted port binding; do not bypass synthetic-auth bind safety by moving the API into a publicly bound container.

## Source of truth and data identities

- PostgreSQL alone owns saved profile revision, immutable approved plan, unique approval identity, idempotency result and minimal audit; a candidate is **never** a durable plan.
- Transient in-process `CandidateLineage` holds owner, latest candidate ID/revision/content hash, captured profile/catalog/validator versions, `expires_at_monotonic`, status (`ready`, `revision_pending`, `approved`, `expired` or `superseded` where relevant), successful-revision count (max **1**), and an in-process async guard. An active revision request's pending token belongs to its lineage. Candidate IDs are opaque; lineage IDs, candidate revisions and hashes never grant authorization.
- One candidate is immutable after publication. Publishing a successful revision at stream terminalization creates a **new ID and hash** and marks the previous candidate superseded. The new approval identity is disclosed to the browser only in a successfully received `done(plan)` (contract `14`); a lost terminal event may leave an orphan that expires and requires fresh generation. The original candidate remains valid *while* the new revision is generating, unless an approval wins first. Revision failure/cancellation releases the pending token and **does not** revoke the previous valid candidate; it can be retried while the revision allowance remains. A successful revision consumes the one-revision allowance across the lineage, even if requested again through a new candidate ID.
- Candidate generation does **not** persist raw prompts, candidate bodies or user chat to PostgreSQL. Proposed capacity ceilings for F1-01 to verify: 30-minute TTL per published candidate; ≤200 active lineages, ≤16 MiB total candidate-store bytes, ≤64 KiB per canonical candidate; ≤16 KiB request JSON. Reject on exhaustion rather than silently evicting an active approval. These are implementation limits to adjust only with an explicit spec update.
- Expired/lost/unapproved candidates require fresh generation and user review. Restart loses all in-memory candidate state, but **does not** lose committed idempotency bindings or approved plans.

## Serialization rule and linearization points

Use a short **per-lineage `asyncio.Lock` (or equivalent)**, shared by approval, publication of a validated revision, and expiry/eviction. Obtain it **only for short state transitions and approval transaction**, never while contacting the LLM, running a long model generation, or waiting for user review. Bound DB statement/transaction timeouts. Do not treat a single-process server as inherently serialized across `async` handlers.

- **Start revision:** under guard, verify identity, current candidate revision, not expired/approved/superseded, no pending revision, and successful revisions <1. Reserve one pending token; release guard. LLM/revision generation takes place outside it.
- **Finish revision successfully:** under guard, re-check owner, status, token, stored profile/catalog/validator freshness, and time. **Only now** atomically publish a new immutable candidate and mark the old one superseded. Clear pending token, consume the single successful revision. If approval committed first, discard generated revision and return `409 candidate_already_approved`, with no new candidate. If candidate expired, return `410 candidate_expired` and discard output. If generation failed/cancelled, clear its pending token under guard; preserve old ready candidate if it has not expired or been approved.
- **Accept first-time approval:** after idempotency lookup (below), acquire same guard; verify owned **terminalized ready** candidate (a candidate in `revision_pending` is still approvable if it is the previous ready candidate) and matching displayed candidate ID, revision and canonical hash; check expiry **at guard acquisition** using monotonic time. This instant is the expiry acceptance point. A candidate accepted before expiry may finish its *bounded* approval DB transaction even if its TTL passes before commit. Pin it against eviction while the guard is held. No candidate accepted after TTL is valid. Validate snapshot and versions again; DB commit is the **approval linearization point**. Mark lineage approved while still guarded after successful commit. DB rollback does not mark approved; if the TTL has elapsed, a new-key attempt cannot newly approve it.
- **Expire/evict:** only under same guard; do not remove an approval in progress. No background sweeper may revoke a state already accepted for an in-flight guarded approval. Post-commit eviction is allowed; persistent idempotency still handles retries.
- **Concurrent revise vs approve:** *revision publication* winning the guard first supersedes old candidate; old approval returns `409 candidate_superseded` and cannot save it. *Approval acquisition* winning first either commits old candidate and blocks revision publication, or rolls back; only after release may pending revision publish if original is still live. Revision may generate while approval is taking place but has no permission to publish before it acquires the guard.
- **Concurrent revisions:** pending token allows one in-flight revision generation per lineage. A second revision request returns `409 revision_in_progress`, and creating new candidate IDs never resets the successful-revision allowance.

## Profile/catalog/validator freshness at DB commit

The approval handler obtains the lineage guard **first**, then opens a short DB transaction; within it lock the owned profile row (`SELECT ... FOR UPDATE` or equivalent), compare the immutable candidate's saved-profile revision to the locked DB revision, and reject mismatch. A concurrent profile Save updates that same row under a DB transaction with optimistic revision checking. Thus Save-first → stale approval rejected, approval-first → approved snapshot commits then Save may update profile. Never take the lineage guard inside profile Save (avoid reversed lock order). The approved record snapshots catalog/profile/validator versions and plan bytes.

For F1 the catalog and validator revision identifiers are **immutable for the lifetime of the process**. Updating their code/data requires process restart, which discards unapproved candidates; no hot mutation. A plan is revalidated against the frozen versions immediately before approval, including the domain duration/constraint rules in `12`. No transaction is held across generation, stream transmission or user review.

## First-time approval vs idempotent committed retry (C5 order)

1. Authenticate principal; validate a bounded request containing `candidate_id`, displayed `revision`, `content_hash` and `idempotency_key` (opaque, bounded length/format). Compute a canonical fingerprint of **all approval-bound fields** including candidate identity, revision and hash (not an untrusted client-supplied plan body).
2. **Before looking up an ephemeral candidate**, query durable idempotency result by unique `(owner_id, 'approve_plan', idempotency_key)`. If committed and fingerprint matches, authorize owned plan read and return the **same plan ID/result**, even if candidate expired, superseded, evicted or lost in process restart. If a committed key exists for that owner with a different fingerprint, return **409 `idempotency_mismatch`** even if candidate is absent. Other owners' keys/results are not disclosed; never query globally by key.
3. Only if the key is new: resolve candidate lineage and acquire its guard; enforce ownership, revision/hash, status and expiry as specified above; revalidate and check frozen versions; then perform the transaction with locked profile revision.
4. Transactionally claim unique `(owner_id, operation, idempotency_key)` and unique `(owner_id, candidate_identity)`; store canonical fingerprint, immutable plan snapshot, and minimal audit/result together. On concurrent same-key collisions, re-read committed owner-scoped result after winner commits: matching fingerprint returns same plan, different fingerprint returns `409 idempotency_mismatch`. On distinct-key attempts for the same candidate identity, exactly one insert succeeds; loser always returns **409 `candidate_already_approved`**, with no new plan. Do not rely on a read-then-insert check alone; DB constraints are the last guard. No partial records on rollback.
5. If DB commit succeeds but HTTP response is lost, step 2 guarantees same-key retry after process restart. New key with missing/expired candidate cannot recover or approve. No claim of exactly-once LLM calls, network delivery or provider charges.

Error contract, with no cross-owner leak: own candidate expired → `410 candidate_expired`; own candidate superseded → `409 candidate_superseded`; revised while approval pending → `409 revision_in_progress` for the second revision; already committed candidate with a **new** key → `409 candidate_already_approved`; unknown/other-owner ID → `404 not_found`; wrong hash/revision → `409 candidate_mismatch`; profile mismatch → `409 stale_profile`; unmatched key payload → `409 idempotency_mismatch`. Internal provider/DB details are never included in user-facing errors.

## Deterministic race/expiry/transaction tests (F1-03/F1-06)

Use barrier/fake-clock-controlled tests—not sleeps—to show:

1. Revision publication acquires guard first, supersedes old candidate; old approval `409 candidate_superseded`, zero persisted plan.
2. Approval acquires guard first, DB commit succeeds; pending revision publication `409 candidate_already_approved`, one immutable plan.
3. Revision request fails/cancels during model run; pending token releases; old unexpired candidate remains approvable; later successful revision consumes exactly one allowance.
4. Two revisions start concurrently; exactly one token; repeated attempts via a new candidate ID cannot exceed the single successful revision.
5. Approval accepted at time `expires_at - ε` and held through expiry may commit; approval accepted at `expires_at` or later fails `410`; expiry sweeper cannot remove guarded approval.
6. Profile Save wins DB row lock before approval → `409 stale_profile`; approval wins row lock first → approved historical snapshot remains immutable after Save.
7. Same-key/same-fingerprint concurrent calls yield one plan and same result; same-key/different-fingerprint yields `409 idempotency_mismatch`; different-key concurrent approval yields one plan and loser `409 candidate_already_approved`.
8. Rollback creates no plan/idempotency/audit; lost HTTP response and process restart still permit matching committed retry with no candidate; wrong-owner and mismatch do not expose plan data.
9. Catalog/validator change forces process restart and loss of unapproved candidates; no mixed-version approval inside a process.

The F1 acceptance report must include exact observed outputs/counts and the limitations of a single API process. No durable run/checkpoint/replay is implied.
